# Windows 虚拟串口终端压力测试（2026-10-07）

**复测更新：驱动 RX 队列已能实际扩至 256 KiB；在此容量下，双向可见／隐藏／
仅接收六项 8M、64 MiB 长测全部通过，384 MiB 数据无丢帧。**
下文前半部分保留最初 4 KiB 队列的失败证据；大队列复测和优化判断见最后一节。

## 已确认的结果

本机 COM1 ↔ COM2 **会在长时间高流量和不限速突发条件下少接收数据帧**。
64 KiB、1 MiB、8 MiB 的基础矩阵 32/32 通过，但 8M、64 MiB 的两个方向长测
均失败。不能用短测试通过推断长时间不会丢帧。

正式矩阵共 36 项：32 PASS / 4 FAIL。另有定位对照，见下文。
包含定位对照后共运行 **48 个数据 case：33 PASS / 15 FAIL**，另有两个驱动
属性查询及校验器／启动预检；它们不计入 48 个数据 case。
所有失败都是完整合法帧缺失，没有发现 CRC 损坏、重复或乱序；失败用例的
串口错误信号与输入泵过载计数仍为零，所以仅看错误信号无法发现此类损失。
本次没有修改生产 SerialTransport、SessionInputPump、Core 或 Renderer。

## 环境与方法

- Windows `10.0.26200.0`，Intel Core i7-14700K，Qt 6.8.3，MSVC 19.51.36260。
- 生产代码基线：`b4e6c951891555f4471ec320eb0fbbcb2c51fc76`，NovaTerm 0.2.65。
- COM1 / COM2 为 `\Device\VSerial9_0` / `\Device\VSerial9_1`，由用户确认互连。
- 8 数据位、无校验、1 停止位，无流控；每次只测试一个方向。
- 使用当前生产 `SerialTransport → SessionInputPump → InteractiveStreamFramer
  → TerminalCore → TerminalRenderer` 通路；真实 D3D11 窗口，1500×800，目标 60 Hz。
  不运行完整 MainWindow，不覆盖会话重连、文件传输、用户交互与真实 UART。
- 128 字节测试帧含十位递增序号、确定性 ASCII 载荷、CRC32/IEEE 和 CRLF。
  接收端按字节流重组，验证全部帧与整流 SHA-256，不把 readyRead 回调当作帧。
- 等待发送端队列、输入泵、解析队列排空并等待 Parser idle；再核对保留文本的
  最后 512 帧。历史上限 10000 行，正常淘汰不计作接收丢帧。
- 发送端的 `sentWrittenBytes` 表示 QSerialPort/驱动完成写入，不是对端已收到。
  因此必须与接收侧计数与 SHA-256 比较，不能单凭 bytesWritten 宣称完整送达。
- “定速”按 8N1 的平均字节率节流：1M / 3M / 5M / 8M 分别对应
  100000 / 300000 / 500000 / 800000 B/s。Windows 调度延迟可能使发送者补发
  积压成大块突发；这不是逐字节模拟真实 UART 线速，后文另做计时对照。

校验器自检包含分片、损坏、缺帧、重复与乱序注入，已通过。
本次只构建／运行独立串口验收夹具，没有运行无关 CTest，也没有进行 sanitizer
验收。生产 Core 目标检查为无需重建；夹具最终增量构建无编译警告／错误。

每项期望 524,288 帧、67,108,864 字节。

| --- | --- | --- | --- | --- | --- |
| COM1 → COM2 | 平均定速 8M | 280989 | 243299 | 46.41% | 35966592 |
| COM2 → COM1 | 平均定速 8M | 287386 | 236902 | 45.19% | 36785408 |
| COM1 → COM2 | 不限速突发 | 119520 | 404768 | 77.20% | 15298560 |
| COM2 → COM1 | 不限速突发 | 120416 | 403872 | 77.03% | 15413248 |

吞吐只有 418.6 / 428.1 KB/s。事件循环最大间隔分别 32.81 / 32.05 ms。
串口原始接收、输入泵接受与 Core 出队三处的字节数相同；Core 水位只有约 8 KiB，
没有解析队列满、输入泵过载或暂停。损失发生在进入 Parser 之前。

## 定位对照

### 驱动队列

以与生产一致的 Qt 串口参数打开端口，查询 GetCommProperties，没有调用
SetupComm 改变驱动配置：两个端口的 `dwCurrentRxQueue` 都为 **4096 字节**，
而 QSerialPort 的软件读缓冲上限为 **262144 字节**，两者不是同一层缓冲。
`dwCurrentTxQueue=0` 表示当前输出队列容量不可用，不能理解为没有输出缓冲。
字段语义见 [Microsoft COMMPROP 文档](https://learn.microsoft.com/en-us/windows/win32/api/winbase/ns-winbase-commprop)。

按 800000 B/s 的平均流量，4 KiB 只能吸收约 **5.12 ms** 的积压。
若接收无法及时排空，或发送者一次补发超过此容量，就存在上游溢出的条件。
这解释了为什么 Qt 256 KiB 软件缓冲与 Core 8 MiB 队列仍不能保护驱动之前的字节。

| 64 MiB 突发，完整终端，延后校验 | COM2 → COM1 | 524288 | 414016 | FAIL |
| 64 MiB 突发，仅 SerialTransport，延后校验 | 两方向各一项 | 524288 | 各 393216 | FAIL，均只收到 16 MiB |
| 8 MiB 突发，4 KiB 发送块，完整终端 | COM1 → COM2 | 65536 | 14976 | FAIL |
| 8 MiB 突发，4 KiB 发送块，完整终端 | COM2 → COM1 | 65536 | 18944 | FAIL |
| 8 MiB 突发，4 KiB 发送块，仅 SerialTransport | 两方向各一项 | 65536 | 各 128 | FAIL，缺失约 0.20% |

仅接收模式没有向 Parser 送数据、没有 GPU 帧，且在接收结束后才做 CRC／序号
验证；因此损失不能解释为 Parser 吞掉输入、历史淘汰、GPU 漏画或在线校验器
占用接收热路径。缩小发送块显著改变结果，支持驱动小队列与排空时序敏感这一
判断，但不能把 4 KiB 分块当作已验证的无损方案。

### 平均流量与瞬时发送时序

COM1 → COM2、8M、64 MiB，仅接收、默认计时策略的对照：

- 实收 321615 / 524288 帧，缺失 202673 帧；
- 最大发送间隔 28.913 ms，最大单次写入 16384 字节；
- 4861 次写入超过驱动 4096 字节接收队列。

Windows 的调度／计时行为使平均限速变成间歇补发，所以该结果不能等同于
真实 UART 每个字节按 8M 线速到达。

采用与既有渲染 benchmark 相同的进程计时精度策略，再运行完整终端：

- 进程策略设置成功；最大发送间隔 3.728 ms，最大写入 2176 字节；
- 没有超过 4 KiB 的单次写入；
- 仍只收到 439818 / 524288 帧，缺失 **84470 帧（16.11%）**。

计时策略改善了发送突发，但没有消除完整终端的长测丢帧。

继续运行相同计时策略的对照，并将全部校验移到接收结束后：

| 通路 | 实收帧 / 期望帧 | 缺失帧 | 最大发送块 B | 最大发送间隔 ms | 事件循环最大间隔 ms | 结果 |
| --- | --- | --- | --- | --- | --- | --- |
| 仅 SerialTransport，延后校验 | 524288 / 524288 | 0 | 2432 | 3.064 | 11.842 | PASS，SHA-256 一致 |
| 完整终端，延后校验 | 248022 / 524288 | 276266 | 2432 | 3.480 | 33.458 | FAIL，缺失 52.69% |

两项均没有超过 4 KiB 的单次发送，平均发送约 800 KB/s。完整终端的原始接收、
输入泵接受与 Core 出队均为 31,746,816 字节，Core 最高水位 6016 字节，没有
过载／背压，CPU 帧 P95 为 7.066 ms。损失仍在进入 Parser 之前。
这组对照排除了在线 CRC 校验器这一混杂因素，并支持终端处理负载下的 GUI
排空时序与 4 KiB 驱动缓冲共同造成上游损失的判断；不能把缺失解释成历史淘汰
或只是未绘制。具体调度、驱动溢出事件及 Qt I/O 内部路径未做更底层追踪，
不能把本轮数据直接定性为虚拟驱动缺陷或 Qt 库缺陷。
不能只依据平均波特率、发送写完成或短测试判断无损。

## 复测与边界

夹具、独立构建说明和 case 参数见
[tests/benchmarks/serial-stress/README.md](../../tests/benchmarks/serial-stress/README.md)。
原始 JSON 与二进制哈希保留在本机 `build/serial-stress-results/`；该目录被
gitignore，不作为其他机器已有测试结果。汇总 CSV 与完整报告用于保留验收证据。
48 项完整汇总见 [case CSV](serial-stress-2026-10-07-cases.csv)。

本次结论限于本机虚拟串口、8N1、无流控、指定 ASCII 帧与对应调度条件，
不能作为真实 UART、其他虚拟驱动、不同流控或所有交互场景的无损保证。
不会把任何失败 case 改成 SKIP 或 PASS，也没有宣称 Windows 全套 CTest 通过。

后续修复应先针对接收侧 I/O 排空时序与驱动缓冲：评估独立串口 I/O 线程、
显式请求并核对驱动接收队列、设备支持的硬件流控，以及可观测的驱动溢出。
调整仍应保留 SessionInputPump 唯一入站通路、有界队列与停止语义；只扩大 Core
队列或修改 Renderer 绘制不能找回进入 Parser 前已丢失的字节。
这些生产改动本轮未实施。

## 排除小驱动队列后的复测与优化空间

### 实验控制已生效

通过同一个 SerialTransport 内部 QSerialPort 的原生句柄调用 SetupComm，
在发送任何测试字节前用 GetCommProperties 再查实际容量。六项长测均核对到
打开时 4096 字节、请求后 **262144 字节**，并非只扩大 Qt 软件缓冲或只看
SetupComm 返回成功。
若容量未确认，夹具会退出 7，不发送测试数据。1 MiB 扩容预检也通过。

此实验纠正了对驱动限制的判断：**4 KiB 是先前当前配置值，不是硬上限**。
本轮只增加测试编译宏下启用的 SerialTransport friend，允许夹具控制同一个端口；
生产目标没有该宏，运行行为与公开 API 不变，主程序仍未应用驱动队列扩容。

### 六项长测结果

条件：8M、8N1、无流控，每项 64 MiB / 524288 帧，稳定计时、延后校验。
每种模式分别运行两个方向，每项约 84 秒。六项均通过整流 SHA-256、全部帧
验证；四项完整终端还通过输入泵／Core 字节核对和末尾 512 帧文本校验。

| 可见终端 | COM1 → COM2 | 0 | 799.829 | 42.29 | 16.982 / 136.742 | 2.946 |
| 可见终端 | COM2 → COM1 | 0 | 799.820 | 49.89 | 15.091 / 31.073 | 4.099 |
| 隐藏终端 | COM1 → COM2 | 0 | 799.958 | 46.90 | 10.809 / 12.037 | 不适用 |

总计 6/6 PASS，384 MiB、3,145,728 帧完整。

没有输入泵过载或暂停，与 8 MiB 队列上限有明显余量。

### 优化判断

**有优化空间，但这组负载下已满足 8M 持续接收的完整性和吞吐要求。**
更大的驱动队列把本机已复现的长测丢帧消除了，不能继续将旧失败直接归因于
Parser 算法的吞吐上限。值得继续优化的方向按优先级为：

1. **应用侧初始化驱动缓冲并验证实际值。** 这是本轮有直接 A/B 证据的改进，
   可作为 Windows 串口连接初始化方案评估；跨平台和拒绝参数的路径仍需处理。
2. **串口接收对 GUI 长延迟的隔离。** 可见终端曾有 136.7 ms 的事件循环间隔，
   本轮 256 KiB 在 800 KB/s 下可容纳约 327.7 ms 积压，因此没有丢帧。
   这只说明本次缓冲足够，不代表 GUI 长延迟已经消失。评估独立 I/O 线程或
   更合理的 GUI 工作预算时，应保留唯一输入通路、有界队列与停止语义。
3. **后台发布与历史布局更新频次。** 隐藏窗口没有 GPU 帧，CPU 仍为 46.9–64.2%，
   比同方向仅接收基线增加约 15.6–32.3 个百分点，且高于同方向可见终端。
   源码仍在 scrollbackChanged 后投递历史布局维护；它按事件循环合并，GUI
   跑得快时仍会退化为每个 Parser 批次一次。发布／布局合并与数据批次大小
   是下一轮采样候选，不应仅以隐藏 GPU 绘制作为后台优化完成的判据。
4. **渲染长尾的进一步采样。** 可见 CPU 帧 P95 为 2.95–4.10 ms，低于 60 Hz
   的 16.67 ms 帧预算。本轮还不足以证明 GPU 上传是主要瓶颈；应先用函数级
   或线程级采样区分布局、快照、信号处理、Qt／驱动等待与系统调度。

CPU 差值不是单个函数的耗时归因，也不能据此承诺某项修改能节省固定比例。
本轮没有实施这些生产优化；保留数据作为后续同机 A/B 的基线。

后续已完成 Windows WPR / xperf 函数采样，优先级进一步收敛到 VT 屏幕同步链。
具体函数、线程占比和收益估算见
[Windows 串口 CPU 热点报告](Performance_Serial_Hotspots_2026-10-07.md)。
